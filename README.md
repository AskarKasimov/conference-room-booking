# Бронирование переговорных

Приложение позволяет выбрать офис и свободную переговорную, посмотреть её расписание, создать бронирование и отменить собственное будущее бронирование. Репозиторий состоит из двух независимых приложений: `server/` — mock-backend на Fastify, `client/` — React SPA на Vite.

## Быстрый запуск

Требуется Node.js 24 или новее.

```bash
# terminal 1
cd server && npm ci && npm run dev

# terminal 2
cp .env.example client/.env && cd client && npm ci && npm run dev
```

После запуска откройте `http://localhost:5173`. API доступен на `http://localhost:3000`

Для запуска сервера с настройками из `server/.env` передайте их оболочке: Node.js не загружает этот файл автоматически.

```bash
cd server
cp .env.example .env
set -a && source .env && set +a
npm run dev
```

## Переменные окружения клиента

Для локального запуска скопируйте корневой `.env.example` в `client/.env`.
Vite загружает переменные из `client/.env`; корневой `.env` использует Docker Compose.

Значения клиента при `SERVER_PORT=3000`:

| Переменная                | Значение                        | Назначение                           |
| ------------------------- | ------------------------------- | ------------------------------------ |
| `VITE_API_BASE_URL`       | `http://localhost:3000`         | обязательный origin REST API         |
| `VITE_WS_URL`             | `ws://localhost:3000/api/v1/ws` | обязательный URL WebSocket           |
| `VITE_REQUEST_TIMEOUT_MS` | `10000`                         | timeout REST-запроса в миллисекундах |

## Команды

```bash
cd client
npm test
npm run check

cd ../server
npm test
npm run check
```

`client npm run check` выполняет Prettier, ESLint, строгую проверку TypeScript, все тесты и production build. В клиентских тестах HTTP заменён MSW, WebSocket — MSW-обработчиком или внедряемой фабрикой; реальный сервер не требуется. `npm test` запускает тесты один раз, `npm run test:watch` — в watch-режиме, как в `server`.

Клиент следует настройкам качества предоставленного backend: одинаковый Prettier, ESLint с проверкой типов (`recommendedTypeChecked`, `projectService`), TypeScript с `strict`, `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`. Исключения ESLint для тестов повторяют серверные. HTTP-клиент принимает внедряемую функцию `fetch`, WebSocket-provider — фабрику соединения; отмена и таймаут HTTP-запросов работают одинаково в тестах и приложении. Тип обработанного WebSocket-события выводится из Zod-схемы и описывает проверенные поля.

## Docker

Собрать и запустить оба приложения в контейнерах можно одной командой:

```bash
docker compose up --build
```

Клиент будет доступен на `http://localhost:5173`, сервер — на `http://localhost:3000`. Для изменения портов и адресов API используйте переменные из `docker-compose.yml`, например `CLIENT_PORT`, `SERVER_PORT`, `VITE_API_BASE_URL` и `VITE_WS_URL`.

### Разработка в Docker

```bash
cp .env.example .env
docker compose -f docker-compose.dev.yml up --build
```

Настройки портов и адресов API находятся в корневом `.env`. По умолчанию фронтенд доступен на `http://localhost:5173`, API — на `http://localhost:3000`.

Dev-compose наследует сервисы через `extends` и выбирает стадии `dev` в Dockerfile. Исходники подключены через volumes: Vite обновляет фронтенд через HMR, `tsx watch` перезапускает бэкенд. Зависимости хранятся в отдельных volumes. После изменения зависимостей выполните `docker compose -f docker-compose.dev.yml run --rm client npm ci` (для бэкенда — `server`). При перезапуске mock-backend данные в памяти сбрасываются.

## Маршруты

- `/` — перенаправляет на `/rooms`;
- `/rooms` — сначала выбор офиса, затем фильтры даты, времени, длительности и вместимости;
- `/rooms/:roomId?date=YYYY-MM-DD` — сведения о комнате и расписание выбранного дня;
- `/bookings` — предстоящие/прошедшие бронирования, фильтр офиса и отмена собственной будущей встречи;
- неизвестные пути — доступная страница 404.

## Технологии

- React 19, TypeScript и Vite;
- React Router DOM для маршрутизации и TanStack Query для кеширования и обновления серверных данных;
- React Hook Form и Zod для формы бронирования и валидации;
- Luxon для вычислений в часовых поясах офисов;
- Radix UI и SCSS-модули для доступных UI-компонентов и стилей;
- Fastify, Zod и WebSocket в mock-backend;
- Vitest и Testing Library; MSW изолирует HTTP-запросы в клиентских тестах.

## Архитектура и принятые решения

Клиент организован по слоям Feature-Sliced Design. `app/` собирает провайдеры, маршруты и глобальные стили; `pages/` отвечает за экраны и URL; `widgets/` объединяет крупные блоки интерфейса; `features/` содержит пользовательские действия; `entities/` владеет типами предметной области, API-endpoints, query keys, запросами и представлениями данных; `shared/` содержит HTTP-транспорт, базовые UI-компоненты, конфигурацию, время и ресурсы. Межслайсовые импорты идут через публичные `index.ts`.

Маршруты объявлены в `client/src/app/router.tsx`. Страницы находятся в `client/src/pages/`; например, поиск комнат собирается в `widgets/room-search`, расписание комнаты — в `widgets/room-schedule`, список бронирований — в `widgets/booking-list`. Формы создания и отмены бронирования остаются сценариями в `features/`. Фильтры списка комнат и дата расписания хранятся в query-параметрах.

TanStack Query хранит серверное состояние. HTTP-транспорт и `ApiError` принадлежат `shared/api`; endpoints и query keys расположены в соответствующих слайсах `entities/office`, `entities/room`, `entities/booking` и `entities/user`. Zod-схема проверяет WebSocket-события в `shared/api`, а соединение и координация инвалидации находятся в `app/realtime`. После `booking.created` и `booking.cancelled` приложение инвалидирует данные бронирований и открытого расписания; после `room.availability_changed` — текущий список комнат, если событие пересекается с выбранным интервалом. Поэтому список доступности и открытое расписание обновляются без перезагрузки страницы.

Время рассчитывается в IANA-часовом поясе выбранного офиса и отображается вместе с его обозначением; для зон с переходом на летнее время используется актуальное смещение. Клиент ограничивает начало будущим моментом не дальше 30 × 24 часов, шагом 15 минут и рабочим интервалом 09:00–20:00 в пределах одного местного дня. Длительность не меньше 15 минут и не может выходить за 20:00. Доступные слоты пересчитываются после смены офиса или даты. Mock-backend остаётся источником истины и повторно проверяет правила: конфликт возвращается как `409 BOOKING_CONFLICT`, после чего клиент обновляет доступность и расписание через REST.

Текущий пользователь загружается через `GET /api/v1/me`; этот endpoint нужен для отображения профиля, собственных встреч в расписании и доступности отмены. Предстоящие встречи сортируются от ближайшей к дальней, прошедшие — от недавней к старой. Отмена доступна только владельцу до момента начала; открытый диалог повторно проверяет время перед `DELETE`. Авторизация не реализована. Обновления WebSocket инвалидируют активные запросы только для соответствующего офиса и пересекающегося интервала; после события экран перечитывает данные через REST.
