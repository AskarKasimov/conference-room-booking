# Бронирование переговорных

Приложение позволяет выбрать офис и свободную переговорную, посмотреть её расписание, создать бронирование и отменить собственное будущее бронирование. Репозиторий состоит из двух независимых приложений: `server/` — mock-backend на Fastify, `client/` — React SPA на Vite.

## Быстрый запуск

Требуется Node.js 20 или новее.

```bash
# terminal 1
cd server && npm ci && npm run dev

# terminal 2
cd client && npm ci && cp .env.example .env && npm run dev
```

После запуска откройте `http://localhost:5173`. API доступен на `http://localhost:3000`

Для запуска сервера с настройками из `server/.env` передайте их оболочке: Node.js не загружает этот файл автоматически.

```bash
cd server
cp .env.example .env
set -a && source .env && set +a
npm run dev
```

## Переменные окружения клиента

Файл `client/.env`:

| Переменная                | Значение в `.env.example`       | Назначение                           |
| ------------------------- | ------------------------------- | ------------------------------------ |
| `VITE_API_BASE_URL`       | `http://localhost:3000`         | обязательный origin REST API         |
| `VITE_WS_URL`             | `ws://localhost:3000/api/v1/ws` | обязательный URL WebSocket           |
| `VITE_REQUEST_TIMEOUT_MS` | `10000`                         | timeout REST-запроса в миллисекундах |

## Команды

```bash
cd client
npm test
npm run check

cd ../server
npm test
npm run check
```

`client npm run check` выполняет Prettier, ESLint, строгую проверку TypeScript, все тесты и production build. В клиентских тестах HTTP заменён MSW, WebSocket — mock factory; реальный сервер не требуется.

## Docker

Собрать и запустить оба приложения в контейнерах можно одной командой:

```bash
docker compose up --build
```

Клиент будет доступен на `http://localhost:5173`, сервер — на `http://localhost:3000`. Для изменения портов и адресов API используйте переменные из `docker-compose.yml`, например `CLIENT_PORT`, `SERVER_PORT`, `VITE_API_BASE_URL` и `VITE_WS_URL`.

## Маршруты

- `/` — перенаправляет на `/rooms`;
- `/rooms` — выбор офиса, даты, времени, длительности и вместимости, список комнат;
- `/rooms/:roomId` — сведения о комнате и расписание рабочего дня;
- `/bookings` — предстоящие/прошедшие бронирования, фильтр офиса и отмена;
- неизвестные пути — доступная страница 404.

## Технологии

- React 18, TypeScript и Vite;
- React Router DOM для маршрутизации и TanStack Query для кеширования и обновления серверных данных;
- React Hook Form и Zod для формы бронирования и валидации;
- Luxon для вычислений в часовых поясах офисов;
- Radix UI и SCSS-модули для доступных UI-компонентов и стилей;
- Fastify, Zod и WebSocket в mock-backend;
- Vitest и Testing Library; MSW изолирует HTTP-запросы в клиентских тестах.

## Архитектура и принятые решения

Клиент разделён по предметным областям: `features/` содержит сценарии поиска, просмотра расписания и бронирования; `components/` — переиспользуемые UI и layout-компоненты; `hooks/` — запросы к API; `api/` — типизированный HTTP-клиент и контракты; `realtime/` — обработку WebSocket-событий. `client/src/router.tsx` связывает экраны из `client/src/routes/` с URL через React Router DOM. Фильтры списка комнат и дата расписания хранятся в query-параметрах.

TanStack Query хранит серверное состояние. После `booking.created` и `booking.cancelled` приложение инвалидирует данные бронирований и открытого расписания; после `room.availability_changed` — текущий список комнат, если событие пересекается с выбранным интервалом. Поэтому список доступности и открытое расписание обновляются без перезагрузки страницы.

Время рассчитывается в часовом поясе выбранного офиса. Клиент ограничивает выбор будущим временем, рабочими часами 09:00–20:00, шагом и минимальной длительностью в 15 минут, а также горизонтом в 30 дней. Mock-backend остаётся источником истины и повторно проверяет эти правила: конфликт возвращается как `409 BOOKING_CONFLICT` и показывается пользователю в форме.

Текущий пользователь загружается через `GET /api/v1/me`; этот endpoint нужен для отображения профиля и собственных встреч в расписании. Авторизация не реализована. Если сервер отвечает конфликтом, клиент запрашивает заново активные данные расписания и доступности через REST, поэтому восстановление не зависит от WebSocket-событий.
